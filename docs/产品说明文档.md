# TalentOS · AI 原生人才培养平台 产品设计文档

## 一、行业调研

### 1.1 政策环境：持续利好，无负面信号

人工智能教育政策自 2024 年起进入密集利好期，核心信号：

- **2024年**《教育强国建设规划纲要（2024—2035）》首次将"促进人工智能助力教育变革"写入国家教育战略纲要。
- **2025年4月** 教育部等九部门《关于加快推进教育数字化的意见》提出"大中小学人工智能教育一体化"。
- **2025年12月** 国家教育数字化战略行动 2.0 将"智能化"列为战略方向。
- **2026年4月**（最新）教育部等五部门联合印发《"人工智能+教育"行动计划》，明确部署"实习实训教学改革"与"AI人才培养一体化"。这是本产品最直接的政策支点。

**市场数据**：中国 AI+教育市场规模 2025 年超 700 亿元，预计 2030 年近 3000 亿元（多鲸研究院），复合增速约 47%。

### 1.2 时机判断

三线交汇：政策驱动（陡峭上扬）× 技术成熟（LLM 多角色扮演/个性化生成已实用化）× 痛点尖锐（实训脱节、企业参与成本高、评价失真）。目前市场上尚无"AI 原生"（非"AI+"贴皮）的高校人才培养平台，窗口期明确。

## 四、知识库准备

### 4.1 测的逻辑（怎么评能力）

**核心理念**：分数不是目的，证据才是。评价体系围绕"证据链"设计——每次对话、每次产出、每次协作都产生可追溯的证据，最终形成可解释的能力报告。

**分数计算链路**：
```
原始证据（对话原话/作品/行为数据）
  → 词典锚点匹配（LLM 将证据映射到 CMO/GEN 词典条目）
  → 等级判定（1-4 级 + 置信度）
  → 百分位换算（z分数 → 正态CDF → 0-100）
  → 分档：<30% 欅佳 / 30-70% 中等 / >70% 优秀
```

**百分位算法**：标准分 z = (原始分-μ)/σ → 正态累积分布CDF(z)×100。常模假设 N(μ=0.40, σ=0.23)，当前为演示参数，接入真实数据后仅替换 μ/σ。

### 4.2 硬技能词典建设

**硬技能 = 知识 + 技能**，两者用不同的原子拆解：

| 类型 | 原子 | 评价方式 | 等级制 |
|---|---|---|---|
| 知识 | 知识点（一个点=一道题） | 选择题/客观题测验 | 二值（会/不会）→ 域级聚合掌握率 |
| 技能 | 任务场景（一个场景=一次产出） | 作品/演练评价 | 四级成长轴（入门/了解/熟练/精通） |

**两条硬规则**：
- **无题不成点**：出不了题的知识点不配入选
- **无任务不成技能**：没有任务场景的技能是空话

**三层复用架构**：通用层（GEN，全岗位）→ 职能层（FPM，产品职能共享）→ 岗位层（GPM，仅限1-2项定制）。新岗位 = 三池组装，词典是基座。

**知识词典示例（AI技术知识·大模型基础）**：

| 知识点 | 定义 | 认知层级 |
|---|---|---|
| LLM工作原理概貌 | 理解"预测下一个词"的生成机制 | 理解 |
| 模型能力边界 | 能列举大模型擅长/不擅长的任务 | 理解 |
| 幻觉及其成因 | 能解释幻觉与生成机制的关系 | 记忆 |
| 上下文窗口 | 能说明上下文长度对任务设计的影响 | 记忆 |

**技能词典示例（评测集设计技能）**：
- L1 入门：按示例补写评测用例
- L2 了解：独立设计覆盖逻辑完整的评测集
- L3 熟练：建立badcase归因-迭代闭环并量化改进
- L4 精通：制定产品评测体系标准

### 4.3 软技能词典建设

**软技能 = 胜任力 + 经历**：

- **胜任力**（可评）：一条胜任力=一根成长轴（四级），每级配6条关键行为锚点，构面降为行为标签（两级结构，保证AI评分时查表扁平性）
- **经历**（不考只沉淀）：沙盘/真题的产出自动归档为证据，不直接评分

**12条胜任力清单**：沟通表达 / 结构化思维 / 跨职能协作 / 用户同理心 / 批判性思维 / 学习敏锐度 / 创新与开放 / 影响与推动 / 抗压与坚韧 / 责任担当 / 伦理与合规意识 / 商业敏感

**胜任力词典示例（沟通表达）**：
- L1 入门：能按模板组织信息、在熟悉话题做简单陈述
- L2 了解：能用"结论-依据-建议"结构汇报工作
- L3 熟练：能在复杂议题中主导沟通、当面改变错误预期
- L4 精通：能在决策会议上一次陈述统一多方立场

### 4.4 编码体系

唯一标识码（入库规范首列）：`CMO-01-沟通表达`（胜任力）/ `GEN-AI技术知识`（通用）/ `FPM-产品方法知识`（职能）/ `GPM-评测集设计技能`（岗位定制）。

## 五、候选人作答端

### 5.1 整体流程

```
登录（手机号+验证码，白名单权限）
  → 初聊画像（陪练官3-5分钟对话 → AI评分 → 能力雷达图报告）
  → 入职（选择学习计划天数 → 领取定制培训包）
  → 工位（三位导师互动 → 课程学习/情景演练/结业考试）
  → 课程闭环（微课→练习→演练→再评→课程完成）
  → 结业考试（三个通用场景 → 100% → 转正评估）
  → 个人中心（基本信息/今日待办/我的成就/我的成长）
```

### 5.2 Agent开发思路

#### 陪练官Agent（初聊诊断）

- **身份**：共事伙伴，不是虚拟面试官。不用简历解析（学生无简历概念），对话即摸底、即语料采集。
- **架构**：主Agent与评分工作流分离——主Agent不含评分逻辑（最小知识原则防套话），评分工作流独立管线（语料→JSON）。
- **意图识别**：五分支（打探评分→挡话术 / 疲惫→友好收尾 / 拒答→不逼问换话题 / 过短→请求展开 / 正常→追问）。
- **追问控制**：单话题≤1次（服务端计数器）+ 总轮次外挂断路器≤3轮。

#### 多角色评审Agent（情景模拟演练）

- **人格Agent三层架构**：

```
数据层（PERSONAS）       结构化人格JSON（身份/性格/知识/说话方式）
    ↓ buildPersonaPrompt()
模板层（Prompt Engine）  人格 + 任务上下文 → 系统提示词
    ↓ llmChat()
输出层（JSON Parser）    {"reply":"台词","satisfied":bool}
```

- **人格是数据不是代码**：改JSON即改性格，运营后台可编辑，同一人格可用于不同场景。
- **任务上下文外挂**：难度、候选人画像、训练目标作为参数注入模板，与人格数据分离。
- **三位Agent人设**：

| 角色 | 人格特征 | 口头禅 |
|---|---|---|
| 张工（研发） | 仔细、直接、技术执着 | "从技术角度看""我需要看到具体的" |
| 刘总（业务） | 急切、商业导向 | "客户等不了""竞品都已经" |
| 陈姐（测试） | 温和、谨慎、切中要害 | "那个我想问一下""边界条件考虑了吗" |

- **Agent调度（三层优先级）**：
  1. 直接点名（用户说"张工你说的…"→张工必须回应）
  2. 未满意+不连续发言（过滤已满意和刚发言的）
  3. 默认轮转（研发→业务→测试，符合真实会议节奏）
- **自然结束**：当≥2个Agent满意（satisfied=true）时温和终止，不硬切。

#### 测评Agent（后测）

- 软技能：复用陪练官对话架构，聚焦课程对应的能力域（5轮对话→前后对比柱状图）
- 硬技能：5道客观题（题库从知识词典生成，含纠偏解析）

## 七、AI Native 设计（核心）

### 7.1 判据

**把AI从产品里抽掉，如果平台依然完整运转，那它只是"AI+"；AI原生意味着抽掉AI，平台失去存在前提。**

本产品中：内容是AI生成的（非预存）、交互是对话式的（非菜单表单）、评价是持续证据链（非节点考试）、教师从内容生产者变为编排者——四个维度都无法回退到传统方案。

### 7.2 意图分流

在每个对话Agent中，用轻量意图识别实现路由：

| 场景 | 意图 → 动作 |
|---|---|
| 初聊Agent | 打探评分→挡话术 / 疲惫→收尾 / 拒答→换话题 / 过短→请求展开 / 正常→追问 |
| 沙盘调度 | 聊技术→张工 / 聊业务→刘总 / 聊测试→陈姐 / 未点名→轮转 |

**设计选择**：用正则/关键词做轻量意图识别（虚拟模式），真AI模式下写入system prompt让LLM自行判断。**不用独立分类器模型**——因为意图类别少（5类以内）、对延迟敏感、且LLM本身能通过prompt完成分流，额外加一层模型增加成本和延迟。

**与Agent协作的关系**：意图分流本质上是同一个架构模式在不同场景的复用——识别用户想做什么 → 路由到合适的处理者。在陪练官里"处理者"是不同回复策略，在沙盘里"处理者"是不同人格Agent。

### 7.3 结构化JSON输出

**为什么用JSON**：
- 机器可读：前端直接消费JSON渲染报告，教师端将来消费同一结构
- 可校验：JSON Schema约束LLM输出格式，解析失败自动降级
- 可追溯：每个字段（reply/satisfied/score）独立可验证

**实现细节**：
```
系统提示词强制要求JSON格式
  → LLM输出（可能包含markdown围栏）
  → 剥离```json围栏
  → JSON.parse（成功→使用reply和satisfied）
  → 失败→正则提取"reply"字段值
  → 彻底失败→纯文本兜底（保证不崩溃）
```

**satisfied信号**：这是控制对话何时结束的关键。每个Agent在每次回复时必须返回布尔值"你对候选人的回答是否满意"。当≥2个Agent满意时，对话温和终止。**之所以用结构化字段而非文本标记**（如让Agent在末尾加[OK]），是因为布尔值不可遗忘、不可格式跑偏、独立于台词内容。

### 7.4 Agent协作 vs Workflow：为什么不做"AI原生多Agent"

**我们的选择是工程编排（workflow），不是自主多Agent**。

**不做真多Agent的理由**：
1. **目的是考学生，不是演话剧**——工程编排保证了技术维度一定被问到、业务压力一定出现、边界条件一定被挑战。真多Agent可能聊了10轮全在聊技术，测试维度漏掉了
2. **成本控制**——每轮只调一次LLM。真多Agent需要并发调用+冲突解决+Agent间协商
3. **可预测性**——评估场景需要可预测的覆盖度，自由对话不可控
4. **行业现状**——业内说的"multi-agent"大多数也是"人格独立、调度统一"的模式

**但我们用了AI原生的地方**：
- 每个Agent的人格由结构化数据+模板引擎动态组装（不是硬编码prompt）
- Agent的回复内容是实时生成的（不是预写脚本）
- Agent的satisfaction信号由LLM自主判断（不由规则硬编码）
- 三层优先级调度是数据驱动的（可配置、可调优）

### 7.5 评分RAG切片

**为什么评分需要RAG**：纯LLM评分有两个问题——打分可以但"写得不像专业测评行业的手笔"（AI味重的大路货评语）。

**我们的做法**：将行业报告撰写规范拆解为独立切片（R1评语规则/R2总评写法/R3培养建议/R4区分性原则），注入评分工作流的system prompt。

**效果**：词典锚点管"打得准"（分数映射到正确维度），RAG切片管"写得专业"（评语符合行业规范：用行为差异而非程度副词、致命不足委婉表达、不同候选人区分性）。

**为什么是few-shot注入而非真RAG**：原型期切片量小（4块），全文注入prompt即可，无检索开销。生产期切片量大后再换向量检索，切片文件不用改。

### 7.6 评分工作流独立（安全设计）

主Agent与评分工作流分离——**最小知识原则**：

- 主Agent的prompt里不含任何评分逻辑
- 用户反向打探评分标准时，主Agent"不是忍住不说，是真的不知道"
- 这是架构级防御，优于在提示词里写"不许透露"（后者在prompt injection面前形同虚设）

另一个理由：陪练和测评是反向目标函数（陪练=鼓励成长，测评=挖透缺点），塞同一个prompt会导致语气漂移。

### 7.7 AI原生的深层表达

- **元层面个性化**：AI导师对四类画像切换四种人格（引路人/陪跑者/护栏教练/冲刺教练）——个性化不只体现在内容，更体现在教学策略本身
- **AI主动召回**：传统App对流失用户只能群发推送，AI导师能基于个人卡点定制召回内容——个性化对象从内容上移到策略层
- **数据飞轮**：企业真题→AI裂变→学生实践→能力画像→企业招聘→更准的岗位数据→吸引更多企业出题——功能可以抄，供给网络和数据飞轮抄不走

## 八、下一步计划

原型验证了架构与体验闭环，后续按三步走，每一步都以"上一阶段被真实使用"为进入条件：

### 阶段一：原型收尾（当前，已完成）

可演示的完整闭环：初聊画像 → 定制培训包 → 工位化学习 → 多 Agent 演练 → 前后测对比 → 结业考试。教师端管理后台、移动端 H5、零依赖 Node 后端均已部署上线。本阶段的产出用于验证设计判断，不追求内容规模。

### 阶段二：MVP 试点（1~3 个月）

目标：**跑通一个真实班级**，用真实使用数据替换演示假设。

| 方向 | 内容 |
|---|---|
| 数据层 | localStorage → 真实数据库，词典/证据/报告按编码体系（CMO/GEN/FPM/GPM）入库，首列 ID 唯一标识 |
| 常模建设 | 百分位参数 μ/σ 从演示假设切换为试点班级真实分布（算法结构不变，只换参数） |
| 教师端闭环 | AI 预批改 → 教师终审全流程可用，验证"AI 生产、教师编排"的分工是否真实减负 |
| 试点设计 | 1 个班级 / 1 门课 / 30~50 名学生，核心观测：完课率、前后测提升幅度、教师干预触发率 |

### 阶段三：规模化与产教融合（3~12 个月）

目标：**从"一个岗位的样板间"变成"岗位群的流水线"**。

- **岗位规模化**：AI 产品经理 → 新道商科/数智岗位群。新岗位走 GEN/FPM/GPM 三池组装，词典复用是边际成本趋零的关键
- **企业侧出题端**：轻量真题上传 → AI 裂变成题 → 教师审核入库——企业从"共建服务"降为"出题即可参与"，降低产教融合的参与门槛
- **技术升级**：few-shot 注入 → 向量检索 RAG（切片文件不用改）；人格库运营化（后台可编辑 JSON 即改性格）
- **数据飞轮启动**：证据链报告 → 企业按画像筛人 → 岗位要求回流 → 词典与常模持续校准

**风险与依赖**：规模化阶段的最大变量不是技术，是内容供给速度（词典验证需要企业侧专家参与）与学校侧的落地配合（教师激励、课时安排）。这也是把"教师做编排者而非盖章员"作为产品设计底线的原因——教师无所得，平台无立足。
